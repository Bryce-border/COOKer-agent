# 面试知识点（按阶段积累，只记录已实现的内容）

## P0 数据层与模型接入

**Q：为什么不直接把菜谱全文丢给向量库，而要做结构化抽取？**
向量检索擅长「语义相似」，不擅长精确约束：「30 分钟内」「不含花生」「我有土豆和鸡蛋」需要结构化字段做过滤和计算；「做 5 人份」需要每份用量。所以规则解析确定性字段，LLM 抽取语义字段，原文保留用于检索与引用。

**Q：LLM 抽取的结果如何保证质量？**
① Pydantic Schema + function calling 约束结构；② 枚举词表 + 校验器归一化；③ 格式错误同厂商重试、再降级；④ 全量后做分布统计和抽检（发现过敏原误标，改为规则推导）；⑤ 回归测试。局限：用量换算仍可能有误差，没有人工标注的评测集——P4 补充。

**Q：增量更新怎么做？**
缓存键 = Prompt 版本 + 原文哈希。上游更新只重算改动的菜；改 Prompt 递增版本号使缓存整体失效。实测二次运行 372 条全部命中、0 token。

**Q：fallback 为什么要在 with_structured_output 之后？**
`with_fallbacks` 返回的 `RunnableWithFallbacks` 不是 ChatModel，没有 `bind_tools`/`with_structured_output`；且主备模型都必须输出同一结构。所以先对每个模型做 transform 再组合。

**Q：并发调用怎么控制？**
`asyncio.gather` 并发 + `asyncio.Semaphore(8)` 限制在途请求数（类比 Java `Semaphore`），防止触发厂商限流；单条失败捕获记录，不影响整体。372 条约 220 秒。

**容易被追问暴露的点**
- 过敏原是关键词规则，会漏标——不能说「保证安全」。
- `total_time_minutes` 是模型预估，不是原文事实。


## P1 检索层与 MCP 工具

**Q：为什么不用向量数据库？**
数据量 1731 块、7MB，暴力余弦是精确 top-k 且毫秒级；ANN 是拿精度换速度，小数据没必要。说清楚迁移阈值（十万级块 / 多进程共享 / 在线增删），以及 `_vector_rank` 是唯一替换点。

**Q：混合检索为什么用 RRF？**
BM25 分数无上界、余弦在 -1~1，直接加权要先归一化，而分数分布还随查询变化。RRF 只看名次，`1/(k+rank)`，k=60 让多路都排前面的文档胜出，又不让某一路的第一名独占。

**Q：父子检索解决什么问题？**
大块召回不准（一道菜混了原料、步骤、附加说明），小块又缺上下文。小块召回 + 菜名前缀 + 按菜聚合，返回整道菜和命中片段。

**Q：外部模型服务挂了会怎样？**
向量失败退回 BM25，重排失败保留 RRF 顺序；熔断器连续失败 2 次断开 60 秒，之后半开试探。项目里真实发生过（embedding 403 / rerank 欠费），这正是加熔断的原因。

**Q：为什么换算和推荐不让 LLM 做？**
确定性问题用代码：可复现、可单测。LLM 负责理解意图、选工具、组织回答。推荐里的多样性重排是 MMR 思想：兼顾单项相关性和结果集的整体覆盖。

**Q：MCP 是什么？工具怎么设计？**
Model Context Protocol：把工具、资源以标准协议暴露给任意 LLM 客户端（类比「AI 的 USB 接口」）。工具描述会直接发给模型，决定它何时调用哪个工具，所以要写清用途和区别（如 search_recipes 与 recommend_by_ingredients）；错误转成可读的 ToolError，模型才能自我修正；返回值精简，节省上下文。

**如实说明的局限**
- 有消融评测（BM25 / 向量 / 混合 / 混合+重排，TD-14），但只有 31 条自写样本；引用数据时要同时说明样本规模。
- 发现过「混合不如纯向量」的反直觉结果，能解释原因（RRF 只看名次）以及为什么仍保留 BM25——这是很好的面试素材。
- 评测集只有 31 条、由开发者自己编写，存在偏差。
- 同义词表手工维护，覆盖有限。

## P2 LangGraph Agent

**Q：讲一下你的 Agent 执行循环。**
StateGraph 三个节点：agent（模型决定调工具还是作答）→ tools（ToolNode 并行执行，结果作为 ToolMessage 回写）→ 回到 agent；
不再调工具时进入 verify，代码检查回答引用的菜是否有工具依据，不通过就删掉回答、附上具体问题让模型重答，最多 2 次。
防死循环：verify 重答上限 + recursion_limit=30。

**Q：怎么防止模型幻觉？**
三层：① Prompt 约束「先查再答」；② 【菜名】引用约定 + 确定性校验；③ 校验失败后用 `tool_choice=required` 强制调工具重答。
用评测量化每一层：qwen-plus 只靠 Prompt 26/36 → 加 verify 30/36 → 加强制调工具 34/36。
诚实补充：verify 只查菜名存在性，不查描述正确性，仍出现过「这道菜能用上土豆」这类错误。

**Q：Prompt 和代码约束怎么分工？**
能用代码判断的就不交给模型：过敏原过滤、用量计算、菜名存在性。Prompt 负责模型擅长的部分：理解意图、选工具、组织语言。
过敏属于安全问题，即使模型忘了传参数，`_filter()` 也会强制排除。

**Q：长期记忆怎么实现？**
LangGraph Store，namespace = ("users", user_id)，存结构化档案；每轮读取写进系统提示词。
短期记忆是 checkpointer 按 thread_id 存消息，发给模型前 trim_messages 裁剪，start_on="human" 保证 tool_call 与结果成对。

**Q：人在回路怎么做？要注意什么？**
`interrupt()` 暂停图并把状态写进 checkpointer，前端拿到问题，用 `Command(resume=答案)` 恢复。
坑：恢复时节点（这里是工具）**从头重新执行**，interrupt 之前不能有副作用，否则会执行两次。

**Q：评测怎么做的？**
12 个场景、每个跑 3 次（模型输出有随机性，单次结果不可信），只判可客观验证的行为：调了哪个工具、参数、档案是否写入、引用是否有依据。
发现过「检查规则太宽松导致 12/12 但实际有幻觉」——之后才加入引用校验。Qwen 与 DeepSeek 对比：DeepSeek 36/36、verify 0 次介入、速度快一倍。

**排查故事（可讲）**
- SQLite 事务冲突：内存版测试没覆盖，第一次修复判断错误，读源码找到 isolation_level 差异。
- langchain-qwq 把 required 静默改成 auto：通过打印最终请求参数发现，直连 API 验证后绕过并加回归测试。

**如实说明的局限**
- 评测 12 个场景是自己写的，规模小；没有回答忠实度（描述正确性）的自动评测。
- 流式输出时被驳回的草稿可能先显示给用户。
