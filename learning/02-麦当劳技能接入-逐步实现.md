## 0. 起点：旧版哪里不对

旧版（归档在分支 `archive/mcd-v1`）的问题，按「怎么发现的」列：

| 问题 | 证据 | 后果 |
|---|---|---|
| Skill 没被当成 Skill 用 | `skills/.../SKILL.md` 复制进来，但没有任何代码读它；`prompts.py` 里另写了 13 条手工压缩的规则，每轮都注入 | 技能的意图路由、三条硬规则丢了；做饭提示词被稀释 |
| 两套产品 | 聊天里只有 3 个只读工具；下单、领券、抽奖在 1206 行的表单页 `/mcd` | 技能本来是为对话设计的；项目里已有 interrupt 确认机制却没用 |
| 正则判断意图 | `routing.py` 用「积分\|优惠\|券…」关键词决定要不要查 | 脆、难测，面试会被问「为什么不让 LLM 路由」 |
| 代码味道 | 同步工具里调 `asyncio.run`；复制了约 5000 行 mclottery 只用了几个函数 | 维护成本高、讲不清 |

值得保留：`client.py` 的读写白名单、线上结构校验、凭据替换；`ledger.py` 的 SQLite 原子认领与「结果未知就冻结」。

**你可以自己练的**：拿到一个「不满意」的旧实现，先写这样一张「问题 / 证据 / 后果」表，再动手。证据要指到文件和行为，不要只写感受。

## 第 1 步：先摸清真实的工具契约（不写业务代码）

## 第 2 步：MCP 客户端 `src/cooker/mcd/client.py`

**核心函数** `call(name, arguments, writing=False)`，一次调用 = 一个独立 MCP 会话：

```
读配置（线程池里读，避免阻塞事件循环）
→ Client(StreamableHttpTransport(官方地址, Token))
→ list_tools → 用「线上」inputSchema 做 jsonschema 校验（参数不对就报错，不发请求）
→ 标记 dispatched=True（写操作从这里开始「可能已执行」）
→ call_tool → 解析 → 把结果里意外出现的 Token 替换掉
```

**几个关键设计**：

1. **两份白名单** `READ_TOOLS` / `WRITE_TOOLS`。不在名单里的工具不会暴露给模型——服务端哪天新增一个写工具，不能被当成只读工具直接执行。
2. **错误分级**：
   - `McdError`：消息可以直接给用户看（不含堆栈和凭据）；
   - `McdUnknown`：写请求**已发出后**超时/断连 → 不能证明没执行。区分点就是 `dispatched` 标志。
3. **单位换算由代码做**：`calculate-price` 返回「分」，`create-order` 用「元」，混用差 100 倍。`for_model()` 给算价结果附一个「金额换算（元）」字段，模型直接引用，不心算。
4. **结果截断**：菜单、营养表可能很长，超过 16000 字符截断并说明，保护上下文。
5. **可替换的传输层** `open_transport()`：测试时换成内存里的假服务（第 8 步）。

**Java 类比**：`call()` 像一个带契约校验的 Feign 客户端；`McdUnknown` 相当于你在支付系统里区分「明确失败」和「超时未知」——后者必须走对账，不能重试。

## 第 3 步：台账 `src/cooker/mcd/ledger.py`

**状态机**：

```
begin → IN_FLIGHT → settle → SUCCESS / FAILED / UNKNOWN
                                          └─ 人工核实后 resolve → SUCCESS / FAILED
```

**三个保证**：

1. **幂等**：主键是 `tool_call_id`。同一次工具调用第二次进来（进程崩溃后重放），只返回记录，不再发请求。
2. **原子认领**：`BEGIN IMMEDIATE` 一开始就拿写锁，「检查冻结 + 抽奖 1 秒频控 + 插入 IN_FLIGHT」在同一个事务里，两个进程不会同时通过检查。
   （Java 类比：`SELECT ... FOR UPDATE` 后再插入，或者数据库唯一约束 + 状态字段。）
3. **冻结**：账户下有 IN_FLIGHT / UNKNOWN 时拒绝一切新写操作。解冻只能人跑命令：

```powershell
.venv\Scripts\python.exe -m cooker.mcd.ledger list
.venv\Scripts\python.exe -m cooker.mcd.ledger resolve <记录号> FAILED --note "App 中无此订单"
```

**为什么解冻不做成工具**：做成工具，模型就可能「为了完成任务」自己解冻。安全边界要放在模型够不着的地方。

**账户怎么区分**：用 Token 的 SHA-256 前 16 位当账户键，换 Token = 换账户，不落盘明文。

## 第 4 步：写操作流程 `src/cooker/mcd/actions.py`（最关键）

`run_write(name, args, call_id)` 的顺序，每一步都有理由：

```
1. 台账里已有 call_id？              → 返回记录（崩溃重放不重发）
2. 账户冻结？                        → FROZEN（别让用户确认一张注定执行不了的卡）
3. 用快照结构校验参数                 → INVALID
4. 用实时只读查询生成确认卡           → 前置条件不满足就 REFUSED，不弹卡
5. 计算卡片指纹 fp
6. answer = interrupt({type:"mcd_confirm", title, rows, warnings, fingerprint: fp})
7. 用户取消                           → CANCELLED
8. answer.fingerprint != fp           → CHANGED（确认期间信息变了）
9. ledger.begin（原子认领）→ client.call(writing=True) → settle
```

### 4.1 为什么确认卡由代码生成

如果让模型写「实付 21 元，确认吗？」，模型算错了，用户也会点确认。所以卡片内容来自代码刚刚做的实时查询：

| 写工具 | 建卡前的实时查询 | 拒绝条件（不弹卡） |
|---|---|---|
| `create-order` | 用同样的购物车重新 `calculate-price` | 外送缺 addressId；到店缺 takeWayCode 或不在算价返回的 takeWayList 里 |
| `draw-lottery` | `query-lottery-info` | 活动不是「进行中」；`drawDecision.resourceEligible` 不为 true |
| `cancel-order` | `query-order` 看当前状态 | 取消原因码不合法 |
| `mall-create-order` | `query-my-account` 看可用积分 | 实物商品没有 addressId |
| `delivery-create-address` | — | 手机号不是 11 位 |
| `auto-bind-coupons` / `party-order-create` | — | — |

### 4.2 interrupt 的坑与指纹

LangGraph 的 `interrupt()` 会暂停整个图，前端用 `Command(resume=…)` 恢复时，**工具函数从头重新执行**（这一点在移除过敏原时已经学过）。所以：

- interrupt 之前只能有只读操作；
- 恢复时卡片会被重新生成。如果两次之间价格或抽奖消耗变了，用户确认的就不是将要执行的内容。

解决：把卡片内容（参数 + 行 + 实时事实）哈希成指纹，随 interrupt 发给前端；前端确认时原样带回；重跑后重新算指纹，不一致就 CHANGED，不执行。

### 4.3 返回给模型的状态

`SUCCESS / CANCELLED / REFUSED / INVALID / CHANGED / FAILED / UNKNOWN / FROZEN`，每种都在宿主适配说明里告诉模型怎么回应（例如 UNKNOWN 禁止重试，引导去 App 核实）。

## 第 5 步：把 36 个 MCP 工具变成 LangChain 工具 `src/cooker/mcd/tools.py`

不手写 36 份 Pydantic 模型，而是：

```python
StructuredTool.from_function(func=run, coroutine=arun, name=name,
                             description=..., args_schema=spec["input_schema"])  # 直接用 JSON Schema
```

开发时先做了一个小实验确认三件事（已验证）：

1. `args_schema` 可以直接是 JSON Schema 字典；
2. 函数签名里写 `runtime: ToolRuntime`，ToolNode 会自动注入，从中拿到 `tool_call_id`（台账幂等键）和 `state`；
3. 同步 `invoke` 走 `func`，异步 `ainvoke` 走 `coroutine`。

**同步 / 异步两个入口**：LangGraph Server 用 `ainvoke`（走 `arun`，真实实现）；CLI 和评测用 `invoke`（走 `run`，在没有事件循环的工作线程里 `asyncio.run(arun(...))`）。
旧版的问题是只有同步入口、在服务器里也用 `asyncio.run`；现在服务器走的是原生异步路径。

**兜底检查**：工具执行时检查 `state["skills"]` 里有没有麦当劳技能，没有就拒绝——工具只在加载技能后才绑定给模型，但模型可能「幻觉」出一个没绑定的工具名，ToolNode 仍会执行它。

写工具的描述末尾追加一段说明：「调用后系统会弹确认卡，参数齐全就直接调用，不要先让用户回复确认」。否则模型会按技能文档先在文字里贴一份确认卡，用户要确认两次。

## 第 6 步：技能按需加载 `src/cooker/skills.py`

三层上下文（渐进式披露）：

| 层 | 内容 | 什么时候进上下文 |
|---|---|---|
| 1 索引 | 每个技能的 name + description | 一直在系统提示词里（约 300 字） |
| 2 正文 | SKILL.md 正文 + 宿主适配说明 + 专用工具 | 模型调用 `load_skill` 之后 |
| 3 参考模块 | `references/*.md` | 模型调用 `read_skill_file` 时 |

**`load_skill` 怎么改状态**：返回 `Command(update={"skills": [name], "messages": [ToolMessage(...)]})`。工具除了返回结果，还能直接更新图状态。

**正文为什么放系统提示词，不放 ToolMessage**：历史消息按 12k token 裁剪（`graph.py` 的 `trim_messages`），一万多字的正文作为一条消息很快会被裁掉，规则就「失忆」了。

**`read_skill_file` 的安全**：只允许读 `skill.files()` 列出的 `references/*.md`（白名单），`../.env`、`SKILL.md`、`LICENSE` 都读不到。白名单比「解析路径再判断是否越界」更简单可靠。

**技能正文不改**：COOKer 与技能文档的差异写在 `src/cooker/mcd/host_adapter.md`，附在正文后面，声明「冲突时以本节为准」。上游技能更新后重新复制即可，不用合并改动。

## 第 7 步：接进图 `src/cooker/agent/graph.py` 与提示词

1. 状态从 `MessagesState` 扩展为 `AgentState`，新增 `skills: Annotated[list[str], _merge_skills]`。`Annotated` 里的第二个参数是 reducer：多次更新时去重合并，而不是覆盖。
2. `get_agent_model(provider, require_tool, skills)`：绑定 `做饭工具 + load_skill/read_skill_file + 已加载技能的工具`。`skills` 是 tuple，作为 `lru_cache` 的键。
3. `ToolNode` 注册**全部**工具（执行端），模型能看到哪些由 `get_agent_model` 决定（调用端）。
4. `prompts.py`：规则加第 8 条「超出做饭范围且命中技能描述时先 load_skill」，模板加「可用技能」索引；已加载的技能把正文拼在最后。
5. `verify.py`：本轮调用过麦当劳工具时，跳过「未加【】的菜名扫描」——麦当劳餐品名可能与菜谱名撞车，会误判。
6. `cli.py`：新增 `ask()`，能在终端里显示麦当劳确认卡并回传指纹。

## 第 8 步：离线测试 `tests/test_mcd.py`

**怎么测会花钱的功能**：用 FastMCP 在内存里起一个假麦当劳服务（`FakeMcd.server()`），测试时把 `client.open_transport` 换成它。这样走的是真实 MCP 协议（initialize → list_tools → call_tool），数据取自技能仓库里的真实结构样例（`tests/fixtures/mcd/`），不连官方服务。

覆盖的场景（17 个，已验证全部通过）：

- 技能：发现与索引、`read_skill_file` 越界拦截、做饭对话不加载、加载后正文与工具生效且跨轮保持、未加载时拒绝麦当劳工具
- 客户端：线上结构校验失败不发请求、写工具不能当读工具调、Token 替换、分→元换算
- 写操作：确认后只执行一次 + 重放不重发、取消不执行、确认期间消耗变化不执行、资格不足不弹卡、超时 → UNKNOWN → 冻结 → 人工解冻、下单卡金额来自实时算价且校验取餐方式、异步路径（服务器用的那条）

**一个测试技巧**：图外直接调 `run_write` 走到 `interrupt()` 会报「不在 runnable 上下文」，用 `monkeypatch.setattr(actions, "interrupt", lambda v: {...})` 替身代替用户点击。

2. 旧版留下的 `data/mcd-actions.sqlite3` 表结构不同，`CREATE TABLE IF NOT EXISTS` 跳过建表导致「no such column」。
   先查了旧库里有没有未结清记录（0 条执行记录），再换新文件名 `mcd-ledger.sqlite3`，没有删除用户数据。
   教训：测试用 `tmp_path` 隔离得很干净，反而测不到「老数据还在」这种情况。

## 自测题

1. 用户确认后、工具重跑之前，抽奖消耗从 24 变成 48。不比对指纹会怎样？比对后用户看到什么？
2. 台账的幂等键为什么是 `tool_call_id`，而不是「工具名 + 参数」？用户合法地连续领两次券时有什么区别？
3. 如果把 SKILL.md 正文作为 `load_skill` 的返回值放进消息历史，十轮对话之后会发生什么？
4. 服务端新增了一个名为 `refund-order` 的工具，运行同步脚本后，它会自动出现在模型面前吗？为什么这样设计？
5. 写请求明确返回「操作太频繁」和请求超时，台账分别记成什么状态？为什么不一样？
