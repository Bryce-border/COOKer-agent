# 图片就地展示 + 按官方文档完善连接器：一步一步怎么做的

> 2026-11-01。设计结论：`docs/technical-decisions.md` TD-26；开发记录：`docs/development-2026-11-01.md` 第二节。
> 前置阅读：`learning/03`（菜谱图）、`learning/05`（商品图走 artifact）。
> 标注：**已验证** = 本次实际跑过；**未验证** = 只有设计或模拟数据。

本次做了两件事：
1. 图片不再放在回答下方，而是贴在**它所描述的那条信息**旁边；
2. 读了麦当劳、瑞幸的官方接入文档，把能用上的信息补进连接器。

# 一、图片就地展示

## 第 1 步：先想清楚「对应的信息」在哪

模型的回答是 Markdown，常见三种结构：

| 结构 | 例子 | 图片放哪 |
|---|---|---|
| 列表 | `- 【清蒸鲈鱼】难度 ★★，鲜嫩` | 整个列表项改成「左图右文」卡片 |
| 表格 | `| 下单立减3元券 | 优惠券 |` | 名称前插一张小图 |
| 段落 / 标题 | `这家店有**生椰拿铁**` | 名称前插一张小图 |

## 第 2 步：关键决策——谁来决定图片放哪？

| 方案 | 问题 |
|---|---|
| A. 让模型在合适位置写 `![](url)` | 要把图片地址交给模型（违反 TD-23 / TD-25 的原则），还可能抄错、截断 |
| B. 让模型写一个占位标记（如 `⟦图:名称⟧`） | 模型要额外遵守一种格式，遵守率不是 100%；漏写就没图 |
| **C. 前端在渲染时按名称自动插图（采用）** | 不改模型输出，确定性；名称本来就要写（【菜名】、商品全名） |

C 的实现位置：**rehype 插件**。react-markdown 的流程是 Markdown 文本 → mdast（Markdown 语法树）→ hast（HTML 语法树）→ React 元素。
rehype 插件在 hast 阶段改树，所以能知道「这个名称在哪个列表项、哪个单元格里」。

**Java 类比**：这像在 DOM 渲染前用一个 Visitor 遍历 AST 改写节点（类似 JavaParser 的 `ModifierVisitor`），而不是渲染后再用字符串替换 HTML。

## 第 3 步：插件 `web/src/lib/inline-images.ts`

输入：`{ recipes: 菜名→封面地址, products: [{name, url}] }`。

```
visit(树):
  遇到块（li / td / h1-h4 / p，li 里的 p 交给 li 处理）:
    findIn(块): 按文档顺序找第一个「有图、且本条回答还没配过」的名称
       - 菜名：linkifyRecipes 把【菜名】变成了 <a href="#recipe:…">，直接认这个链接
       - 商品名：在文本节点里找；「生椰拿铁（原创）」也匹配「生椰拿铁」；长名称优先（防「拿铁」抢走「生椰拿铁」）
       - 不进入嵌套列表、表格、代码块（它们各自处理 / 不配图）
    apply:
       - li 且该名称是这一项「第一个出现的名称」→ 左图右文；所在列表加 .cooker-media-list
       - 否则 → 在名称前插入小图（文本节点从名称处切开）
    继续访问子节点（嵌套列表）
```

插入的 `<img>` 带 `data-inline-image="media|inline"`、`data-image-kind`、`data-recipe`。`markdown-text.tsx` 的 `img` 组件据此渲染：
菜谱图可点击打开菜谱抽屉；商品图 `object-contain`（瑞幸是透明底的杯子图）；都加 `referrerPolicy="no-referrer"`。
没有这些标记的图片（回答里本来的 Markdown 图片，如瑞幸支付二维码）限制最大尺寸、加圆角边框。

## 第 4 步：真实回答暴露的两个样式问题（已验证并修复）

用真实模型问「推荐几道适合周末做的海鲜菜」后截图：

1. **图片挂错位置**：「小提示」一项是「【咖喱炒蟹】口味带辣…；【蛏抱蛋】热量偏高」，咖喱炒蟹没有图、蛏抱蛋有图。
   第一版把蛏抱蛋的图放在整项最左边，看起来像是咖喱炒蟹的图。
   → 规则改为：**只有这一项第一个出现的名称有图时才用左图右文**；否则在对应名称前插小图。实现上 `findIn` 记录「前面是否已出现过别的名称」（没图或已配过图的名称也算）。
2. **同一列表样式不统一**：有图的项是卡片，没图的项还是圆点。
   → 列表里只要有一项配了图，就给整个列表加 `.cooker-media-list`，没图的项也用卡片样式，并留出图片宽度让文字对齐。

## 第 5 步：数据从哪来（`messages/ai.tsx`）

- 菜谱封面：`useRecipeCovers(text, enabled)`（原来的图片条组件改成了只取数据的 hook，批量请求 + 缓存不变）。
- 商品图：`turnImages(messages, messageId)`，取本轮工具消息的 `artifact.images`（跳过 verify 的隐藏消息，见 learning/05）。
- 流式输出期间 `enabled=false`，不插图，避免页面跳动。
- hooks 必须放在组件里任何 `return` 之前（React 的 hooks 规则：每次渲染调用顺序必须一致）。

## 第 5.5 步：图片太小（用户反馈后调整）

第一版列表图 64px、行内图 28px，表格里的商品几乎看不清。调整为列表 96px、行内 56px；商品图可点击放大（portal 到 body 的遮罩层，
避免在 `<p>` / `<td>` 里嵌 `<div>` 造成非法 DOM 嵌套），菜谱图点击仍打开菜谱抽屉。回归脚本加了「行内图 ≥ 48px」断言，防止以后被改小。

## 第 5.6 步：版式重做——「放大」不是答案（用户反馈后）

只加点击放大并没有解决问题：用户要的是在页面里**直接**看得清。这次重新设计尺寸和放法：

| 位置 | 之前 | 现在 |
|---|---|---|
| 列表项（第一个名称有图） | 左侧 64px | 卡片，左侧 128px（窄屏 88px） |
| 列表项里其余有图的名称 | 不配图（只配第一个） | 项末尾的图片行 |
| 段落 / 标题 | 名称前 28px 小图 | 这一段下方 144px 图片行，带名称 |
| 表格 | 28px | 64px |

几个设计点：

- **段落里不再插行内图**：几十像素的图塞进一行字里，图和字都难看清；放在段落下方的图片行，名称写在图下，仍然紧贴对应的话。
- **每个名称都配图**：`findAll` 收集块里所有有图名称（之前 `findIn` 只返回第一个）。表格里多个名称时倒序插入，前面的位置不受影响。
- **列表用 CSS 网格两列**（图 / 正文）：没图的项用 `::before` 占住图片列，正文对齐；第一版给它画了 128px「暂无图片」灰块，截图一看又空又重，改成只占位不画。
  网格要求每项只有两个格子，所以插件会给没配图的项也包一层正文容器（否则零散的文字节点各占一格）。
- **整体版式**：模型常用 `##` 写小标题，原来是 30px 的文章标题，太抢眼 → 18px 加橙色竖条；表格包一层圆角外框并允许横向滚动（窄屏不撑破）；引用块多用于提醒 → 浅琥珀底色，不用斜体。
- **回归脚本断言实际尺寸**（`boundingBox`）：卡片图 ≥ 120px、图片行 ≥ 140px、表格 ≥ 60px，防止以后被改小。

**教训**：用户说「太小看不清」，要解决的是默认状态下的可读性，交互补救（放大）只能是附加功能。

## 第 6 步：验证（已验证）

| 检查 | 结果 |
|---|---|
| `verify-recipe-covers.mjs`（预置会话） | 有图的菜在**自己的列表项**里左图右文；无图 / 库外菜不配图；「第一个菜没图、后面的菜有图」那一项不是卡片布局，小图插在后者名称前；点击图片打开抽屉 |
| `verify-product-images.mjs`（预置会话） | 段落里「生椰拿铁」前、表格单元格「橙C美式」前各一张图；同一商品提到两次只配一张；未提到的不显示 |
| `--real`（瑞幸） / `--real-mcd`（麦当劳奖品表格） | 图片在对应文字 / 单元格旁，真实加载（麦当劳 8 张奖品图配在各自行；接口没给图的 2 项不配图） |
| 真实菜谱推荐 | 5 张封面在各自列表项 |

# 二、按官方文档完善连接器

## 第 7 步：读文档，挑出能用上的信息

| 文档里的信息 | 之前的状态 | 做了什么 |
|---|---|---|
| 瑞幸 `queryOrderDetailInfo.orderStatus`：10 待付款 / 20 下单成功 / 30 制作中 / 60 等待取餐 / 80 已完成 / 100 已取消；金额 `orderPayAmount`；商品 `orderCommodityList` | 取消卡靠「猜字段名」 | 取消卡按文档字段生成；80 / 100 直接拒绝；30 / 60 加「门店可能无法取消」提醒 |
| 瑞幸 `createOrder.orderId` 是 19 位数字（示例 7639308439653908490），另有字符串 `orderIdStr` | 原样给模型 | 换成字符串（见第 8 步） |
| 瑞幸 `needPay=false` 表示无需支付；`switchProduct` 选中属性 `operation=3` | 不知道 | 写进宿主适配说明 |
| 瑞幸使用示例「帮我看一下最近的订单」，但**没有订单列表接口** | 做不到 | 新增本地工具 `luckin_recent_orders`（第 9 步） |
| 麦当劳错误码：401 Token 无效 / 过期，429 超过 600 次/分钟 | 统一提示「服务暂不可用」 | 明确提示（第 10 步） |
| 麦当劳订单状态「订单已完成」「订单已取消」 | 照样弹取消卡 | 直接拒绝 |

**未采用 / 留作方案**：麦当劳 1.0.9 起堂食外带返回取餐柜二维码（`lockerQrCode`），可以像支付二维码一样展示——没有真实订单无法确认字段与图床，暂不做。

## 第 8 步：19 位订单号为什么要换成字符串

JavaScript 的数字是 IEEE 754 双精度浮点，只能精确表示到 2^53（约 9×10^15，16 位）。
`7639308439653908490` 有 19 位，前端 `JSON.parse` 后会变成 `7639308439653908000`——订单号就错了。
Python 的 int 没有这个问题，所以后端看着一切正常，只有到了浏览器才出错。官方返回里同时给了 `orderIdStr`，`present` 里直接用它替换。

**Java 类比**：和 Java 后端把 `Long` 型 ID 返回给前端时要序列化成字符串（Jackson `ToStringSerializer`）是同一个问题。

## 第 9 步：没有接口的「最近订单」——复用台账

瑞幸只能按订单号查订单。但每次经 COOKer 下单，台账都记录了完整返回（包括订单号）。于是：

- `Ledger.history(account, tool, limit)`：查某账户某写工具的成功记录；
- 连接器框架加一个扩展点 `Connector.local_tools`：宿主提供的本地工具（不经过 MCP），随技能一起绑定；
- 瑞幸的 `luckin_recent_orders`：读台账，返回订单号、下单时间、应付金额，并明确说明「只含本机经 COOKer 下的单」。

两个实现细节：

1. **写成同步函数**。最初写成 `async def`，只有异步入口——CLI 和评测用的同步 `invoke` 会直接报不支持。台账读写本来就是同步 SQLite，同步函数在服务器里会被放进线程池执行。
2. **和 `run_write` 用同一个台账入口**（`actions.Ledger`）。最初直接 `Ledger()`，测试时读到的是本机真实台账而不是测试台账——说明读写可能落到不同文件。统一入口后，写入和读取一定是同一个台账。

## 第 10 步：401 / 429 提示，以及一个差点上线的 bug

**问题**：用错误 Token 测试，两个服务都只得到 `MCPError: Server returned an error response`（JSON-RPC -32603），没有 HTTP 状态码——MCP SDK 把它吞了。

**方案**：传输层支持自定义 httpx 客户端工厂（`httpx_client_factory`）。在工厂里给客户端挂一个响应钩子，把 ≥400 的状态码记下来；调用失败时按状态码给出提示。
安全约束：**只在写请求还没发出时**才这样翻译；写请求已发出，即使看到错误码也按「结果未知」处理。

**bug**：第一版工厂签名是 `(headers, timeout, auth)`，但 fastmcp 调用时还会传 `follow_redirects=True`，于是每次调用都在工厂里抛 TypeError，
**所有真实调用都失败了**。离线测试用的是假传输层，完全没发现；是用错误 Token 做真实探测时，看到「钩子一个状态码都没记到」，才去读 fastmcp 源码找到原因。
修复：签名加 `**_` 接住多余参数；并补了一个测试，**按 fastmcp 的实际调用方式**调用工厂。

**教训**：

- 离线假服务能测业务逻辑，测不到「和真实库的接缝」。改了接缝（这里是传输层），一定要用真实调用跑一次。
- 结果不符合预期时（钩子没记到），先打印证据再推理，不要换个写法碰运气。

修复后（已验证）：错误 Token → 「密钥无效或已过期：请到瑞幸 MCP 开放平台重新获取 Token，更新本机 config/luckin-mcp.local.env」；真实 Token 调用正常。

## 自测题

1. 为什么在 rehype 阶段插图，而不是渲染后对 HTML 做字符串替换？
2. 「第一个出现的名称」规则解决了什么问题？如果去掉它，举一个会误导用户的例子。
3. 19 位订单号在 Python 里没问题、在浏览器里出错，根本原因是什么？
4. 为什么写请求发出后看到 429，也不能判定为「没执行」？
5. 离线测试全部通过，真实调用却全部失败——这种情况说明测试缺了哪一层？

## 附：一次「测试失败但代码没错」的排查

麦当劳确认卡回归（让模型一键领券）突然失败。给脚本加上失败诊断（打印会话消息）后看到：模型先查可领券，发现都已领过，于是正确地不调用领券。
测试依赖了会被真实操作改变的账户状态。改用不依赖账户状态的写操作（新增地址，只点取消）。**教训**：端到端测试要选「每次前置条件都成立」的场景，并且失败时要能打印足够的现场。
