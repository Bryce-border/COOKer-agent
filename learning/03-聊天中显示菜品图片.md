# 聊天中显示菜品图片：一步一步怎么做的

> **2026-11-01 更新**：图片不再显示在回答下方，改为插到对应菜名所在的列表项 / 菜名旁（`web/src/lib/inline-images.ts`，见 `learning/06`）。取图、封面选择、缓存与请求去重的思路不变；原来的 `RecipeCovers` 组件已改为 `useRecipeCovers` hook。

> 2026-10-31。设计结论精简版见 `docs/technical-decisions.md` TD-23。标注：**已验证** = 本次实际跑过。

## 0. 需求与现状

需求：回答里提到的菜如果有图片，直接在聊天框里展示。

先摸现状（不急着写代码）：

- 菜谱库 372 道菜，**179 道有图**，大多是 HowToCook 仓库里的本地 jpg，只有 2 张是外链。
- 图片已有接口 `GET /cooker/images/...`（带路径穿越防护），菜谱抽屉里已经在展示。
- 回答里的库内菜名约定写成【菜名】，前端已把它改写成可点击的菜名按钮。

所以真正要做的只有：**从回答里找出菜名 → 找到每道菜的封面 → 在回答下方显示。**

## 1. 关键决策：图片由谁放进聊天？

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 让模型输出 Markdown 图片 `![](url)` | 工具结果里带图片地址，模型照抄 | 模型可能抄错、编造地址；每次都多花 token；每条回答图片多少不可控 |
| B. 工具返回后前端直接画 | 在 ToolMessage 下方渲染图片 | 工具查到的菜不等于最终推荐的菜（会查 5 道、只推荐 2 道） |
| **C. 前端按回答里的【菜名】去取图（采用）** | 回答结束后，前端提取【菜名】，批量请求封面接口 | 只展示模型真正推荐的菜；图片地址来自菜谱库，不经过模型 |

C 复用了已有的【菜名】约定，和「菜谱抽屉不经过 LLM、零 token」是同一个思路：**确定性的数据由代码去取，模型只负责说话。**

## 2. 第二个发现：第一张图不一定是成品图

统计多图菜谱的文件名（已验证）：

```
清蒸鲈鱼 ['改刀', '摆盘', '清蒸鲈鱼']
糖醋鲤鱼 ['腌制', '成品']
冬瓜酿肉 ['冬瓜酿肉成品', '冬瓜形状', ...]
回锅肉   ['1', '2']
```

HowToCook 的图常按步骤排列，直接取第一张会把「改刀」当封面。于是写了 `pick_cover()`（`src/cooker/api.py`），按文件名打分：

1. 含「成品 / 做好 / 完成 / result / final」→ 3 分
2. 文件名与菜名相同或互相包含（如 `清蒸鲈鱼.jpg`）→ 2 分
3. 含「摆盘」→ 1 分
4. 其余 0 分；同分保留原文顺序（`max()` 遇到同分返回第一个）

这是启发式规则，不保证每道菜都选对（比如 `1.jpg`、`2.jpg` 只能取第一张），但对常见命名有效，而且可测试。
顺手让菜谱详情接口也把封面排到第一张，抽屉和聊天里看到的是同一张图。

## 3. 后端：批量封面接口

```
GET /cooker/covers?names=蒜蓉虾&names=清蒸生蚝&names=黄油煎虾
→ {"covers": [{"query": "蒜蓉虾", "name": "蒜蓉虾", "image": "/cooker/images/dishes/..."}]}
```

- **为什么批量**：一条回答常推荐 3–6 道菜，逐个请求就是 N 次往返；批量是 1 次。
- 查不到的菜、没有图的菜**静默跳过**（回答里的【】偶尔不是库内菜，verify 节点会兜底，这里不报错）。
- 限制最多 8 个名字、每个 ≤ 50 字（防止被当成批量查询接口滥用）。
- 返回 `query`（回答里写的名字）和 `name`（库里正式名）：用户写「番茄炒蛋」，库里叫「西红柿炒鸡蛋」，前端缓存按 `query` 记。
- 和其他自定义路由一样写成同步 `def`，Starlette 放进线程池，不阻塞同进程的流式对话。

## 4. 前端

`web/src/lib/cooker.ts`：

- `citedRecipes(text)`：用和 `linkifyRecipes` 同一个正则提取【菜名】，去重并保持顺序。
- `fetchCovers(apiUrl, names)`：
  - **结果缓存**（`coverCache`）：同一道菜在多条回答里出现只请求一次；`null` 表示「查过、没有图」，也要缓存，否则会反复请求。
  - **请求中去重**（`pending`）：见第 5 节的问题。
  - 失败不写缓存，下次还能重试。

`web/src/components/cooker/recipe-covers.tsx`：

- 回答下方横向滚动的图片卡片（最多 6 张），点击打开已有的菜谱抽屉。
- `enabled = !(isLoading && isLastMessage)`：**流式输出期间不请求**。否则菜名逐字出现（「清」「清蒸」「清蒸鲈」……）会不断触发请求。
- `loading="lazy"`：翻到历史消息时才加载图片。
- 请求失败直接不显示：图片是锦上添花，不能打扰对话。

## 5. 真实环境才暴露的问题：同一批菜名请求了两次

用真实模型跑「推荐几道周末海鲜菜」，抓到 `/cooker/covers` 请求了 **2 次**，参数完全相同（已验证）。

原因：开发模式下 React 严格模式会把 effect 执行两遍（挂载 → 卸载 → 再挂载）。缓存是在响应回来后才写入的，第二次执行时缓存仍是空的，于是又发一次。生产环境不会重复挂载，但多条回答同时渲染时同样可能并发请求同一道菜。

修复：把「正在请求中」也记下来（`pending: Map<菜名, Promise>`），后来的调用直接等同一个 Promise。
连带改动：共享请求不能再接受某个调用方的 `AbortSignal`（一个组件卸载就取消请求，会让其他等待者一起失败），组件改用 `stale` 标志忽略过期结果。修复后实测请求 **1 次**（已验证）。

**Java 类比**：这就是缓存击穿时的「单飞」（single-flight）——Guava `LoadingCache` 对同一个 key 并发 `get` 只加载一次，其余线程等待同一个结果。

| 前端 `tsc --noEmit`、eslint | 通过 |
| 浏览器回归 `web/scripts/verify-recipe-covers.mjs`（预置会话，不调模型） | 两道有图的菜显示封面且图片真实加载；无图菜与库外菜不显示；点击打开抽屉 |
| 真实模型「推荐几道周末海鲜菜」 | 回答结束后显示 4 张成品图；封面请求 1 次；无页面错误 |
| 生产构建 `pnpm build` | **本次未跑**（3000 端口有开发服务占用 `.next`） |

测试中还踩了一个坑：用 `updateState(..., asNode: "agent")` 预置会话时，图会认为下一步该执行 verify，页面显示「需要你确认 when: breakpoint」。改成 `asNode: "verify"`，表示这条回答已经过了校验、图已结束。

## 7. 局限

- 封面靠文件名猜，`1.jpg / 2.jpg` 这类命名无法判断哪张是成品。
- 193 道菜没有图，只能不显示；没有做占位图（占位图没有信息量）。
- 原图中位数约 211 KB、最大约 1 MB，没有生成缩略图；卡片只有 144×96 像素，流量偏大。可选优化：入库时用 Pillow 生成缩略图（需新增依赖）。
