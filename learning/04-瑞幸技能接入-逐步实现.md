# 瑞幸咖啡技能接入：一步一步怎么做的

> 2026-10-31。对应设计结论：`docs/technical-decisions.md` TD-24；开发记录：`docs/development-2026-10-31.md` 末节。
> 前置阅读：`learning/02-麦当劳技能接入-逐步实现.md`（技能按需加载、确认卡、台账的原理都在那里，本文不重复）。
> 标注：**已验证** = 本次实际跑过；**未验证** = 只有设计或模拟测试。

## 0. 输入：一个技能包 + 一个 Token

用户给了两样东西：`my-coffee-skill.zip` 和瑞幸 MCP 的 Token。接入目标：在 COOKer 聊天里点瑞幸，且「花钱」的操作和麦当劳一样安全。

---

## 第 1 步：先读技能包，再决定怎么接（不写代码）

**安全习惯**：下载来的压缩包是不可信数据。解压到一个新建的空目录（`learning/scratch/coffee-skill-src/`），只读文件，不执行里面任何脚本。

包里只有 4 个文件：`SKILL.md`、`manifest.json`、`CHANGELOG.md`、`LICENSE`。读完记下影响设计的 4 点：

| 发现 | 影响 |
|---|---|
| LICENSE 是 **CC BY-ND 4.0**（署名、禁止演绎） | 可以原样再分发，**不能改正文**。正好沿用「正文原样 + 宿主适配说明」的做法 |
| 技能假设宿主有 shell：用 curl 调接口、用 ipinfo.io 按 IP 定位、把 Token 写到 `~/.my-coffee/` | COOKer 的 Agent 没有命令行，这几条必须在适配说明里**明确覆盖** |
| 写操作只有 `createOrder`、`cancelOrder` | 确认卡只需写两张 |
| 硬约束：先 `previewOrder` 再下单、券码 `couponCodeList` 原样透传、用门店坐标下单、不展示 `payOrderUrl` | 这些都能用代码保证，不应只靠提示词 |

**你可以练的**：读第三方技能时，把每条规则分成三类——①宿主环境相关（要适配）②能被代码机械检查的（写进代码）③需要理解语境的（留给提示词）。

---

## 第 2 步：Token 存放（凭据安全）

- Token 写进 `config/luckin-mcp.local.env`，**不进 Git**。`.gitignore` 从 `/config/mcd-mcp.local.env` 改成 `/config/*.local.env`，以后新增服务不会忘。
- 提交一个不含密钥的模板 `config/luckin-mcp.example.env`。
- 用 `git check-ignore -v` 确认真实文件确实被忽略（已验证）。
- 技能的「读取优先级：环境变量 > 对话里给的 Token > 本地文件」里，「对话里给的」在 COOKer 不适用：模型永远拿不到 Token，也不该让用户在对话里发送。

⚠️ 这次 Token 是在对话里发给助手的，会留在聊天记录中。测试完成后建议到瑞幸 MCP 开放平台重新生成一个。

## 第 3 步：摸清真实契约（只读）

和麦当劳一样，先只调用 `list_tools`（协议层「列出工具」，不碰账户）：

- 8 个工具，与技能文档一致。描述很短（如「瑞幸咖啡订单预览」），规则全在 SKILL.md。
- 入参结构里有一个**非标准字段** `returnDirect: false`。它不是 JSON Schema 的一部分，原样交给模型接口可能被拒收 → 同步快照时去掉。

再用只读工具摸返回结构（门店 → 商品 → 详情 → 预览，`previewOrder` 只预览不建单）。为确认卡设计拿到的关键事实（已验证）：

```text
queryShopList   → {"code":0,"data":[{deptId, deptName, address, longitude, latitude, workTimeStart/End, distance, workStatus:"打烊中"}]}
searchProductForMcp → productId, skuCode, productAttrs, initialPrice:20.0, estimatePrice:20.0
previewOrder    → totalInitialPrice:20.0, privilegeMoney:0.0, discountPrice:20.0, couponCodeList:[],
                  shopInfo{deptId, 坐标, workStatus}, productInfoList[{productId, skuCode, amount, additionDesc:"大杯/冰/…"}]
```

- **金额单位是「元」**（20.0），和麦当劳算价的「分」不同——每个服务的单位都要实测，不能类推。
- 晚上测试时门店全部「打烊中」→ 卡片要能提示门店状态。

## 第 4 步：关键决策——复制一份麦当劳代码，还是抽象？

对比两边需要的东西：

| | 麦当劳 | 瑞幸 |
|---|---|---|
| 技能按需加载、工具结构快照 | 要 | 要 |
| 读写白名单、线上结构校验、凭据替换 | 要 | 要 |
| 确认卡 → interrupt → 指纹 → 台账 | 要 | 要 |
| 官方地址、凭据文件、工具名单 | 不同 | 不同 |
| 确认卡内容 | 7 张 | 2 张 |

相同的部分占绝大多数。复制一份意味着两套安全逻辑以后各改各的（比如修了麦当劳台账的 bug，瑞幸忘了修）。
所以决定**把麦当劳的实现提成通用层**，每个服务只提供差异。

**Java 类比**：这是模板方法 / 策略模式。`run_write` 是固定的流程骨架；每个服务通过 `Connector` 注入自己的「策略」（白名单、确认卡函数）。像 Spring 里一个通用 `PaymentService` + 多个 `PaymentProvider` 实现。

---

## 第 5 步：抽出通用层 `src/cooker/connectors/`

| 文件 | 来自 | 变化 |
|---|---|---|
| `base.py` | 新增 | `Connector` 数据类：`key / label / skill / url / env_prefix / env_file / package_dir / read_tools / write_tools / cards / app_hint / present` |
| `client.py` | `mcd/client.py` | 所有函数多一个 `conn` 参数；错误信息用 `conn.label` |
| `actions.py` | `mcd/actions.py` 的流程部分 | `run_write(conn, …)`；卡片函数从 `conn.cards[name]` 取 |
| `ledger.py` | `mcd/ledger.py` | 文件改名 `data/connector-ledger.sqlite3` |
| `tools.py` | `mcd/tools.py` | `make_tools(conn)` |
| `__init__.py` | 新增 | `all_connectors()` 登记全部服务 |

几个值得讲的细节：

1. **`Connector.__post_init__` 断言每个写工具都有确认卡**。以后有人把新工具加进 `WRITE_TOOLS` 却忘了写卡片，程序启动就报错，而不是到运行时才出问题。
2. **`all_connectors()` 断言不同服务的工具不重名**。ToolNode 按名字找工具，重名会调错服务（麦当劳是 `create-order`，瑞幸是 `createOrder`，目前不冲突）。
3. **凭据读取**：环境变量优先于配置文件（和 pydantic-settings、技能自己的约定一致）；地址必须等于官方端点，防止配置笔误把 Token 发到别处。
4. **台账账户键 = 服务 + Token 摘要**：瑞幸一笔结果未知只冻结瑞幸，麦当劳照常可用。
5. **延迟导入**：`all_connectors()` 在函数里才 import 各服务，入库、检索评测这些不涉及外部服务的场景不加载 MCP 依赖。

麦当劳随之变成 `mcd/connector.py`：白名单 + 7 个卡片函数 + 分→元换算，原来的 client / actions / tools / config 都删掉了。

**怎么证明重构没改坏**：麦当劳原有 17 个测试，只改 import 和函数调用方式、**不改任何断言**，全部通过（已验证）。这是重构的基本纪律：先有测试，再动结构。

**一个插曲**：改名台账文件前查了一下里面的内容，发现有 1 条真实 SUCCESS 记录——当天 11:12:59 的「一键领券」，成功领了 3 张券。这不是自动测试产生的（测试都用临时目录），按设计只有在确认卡上点「确认」才会写入，说明是用户在网页上自己确认的。
结论：写操作链路在真实账户上跑通过一次；改名时原样保留数据（`mv`，不重建）。**教训**：动用户数据文件之前先看里面有什么。

## 第 6 步：瑞幸连接器 `src/cooker/luckin/connector.py`（115 行）

### 6.1 读写分类

- 写：`createOrder`、`cancelOrder`。
- 读：`queryShopList`、`searchProductForMcp`、`queryProductDetailInfo`、`queryOrderDetailInfo`，以及
  `switchProduct`（只是按属性换算出新 SKU）、`previewOrder`（只预览不建单）——没有副作用，归为读。

### 6.2 下单确认卡：把技能的硬约束写成代码

```
createOrder(模型给的参数)
  → 实时 previewOrder(deptId, productList)
  → 检查：预览有应付金额？预览的商品/SKU/数量与下单参数一致？门店一致？   不满足 → REFUSED，不弹卡
  → 最终参数 = 模型参数
               + couponCodeList = 预览返回的券码（原样透传；模型漏传或传错都被覆盖）
               + longitude/latitude = 预览返回的门店坐标（技能要求用门店坐标）
  → 卡片：门店、到店自取、商品×数量（规格描述）、原价、减免、应付、优惠券张数；门店不在营业则加提示
  → Card(args=最终参数) —— 最终参数参与指纹，用户确认的就是实际执行的
```

为此给通用层的 `Card` 加了一个字段 `args`：卡片函数可以用实时数据**改写最终参数**。这是这次抽象里唯一为瑞幸新增的能力。

**为什么不只在提示词里要求「必须透传券码」**：模型照做的概率很高但不是 100%；漏传的后果是按原价下单、用户多花钱。能用代码保证的约束，就不要赌模型的服从率。

### 6.3 取消确认卡

先 `queryOrderDetailInfo` 查订单状态再出卡。**未验证**：没有真实订单，不知道详情的确切字段名，所以按常见命名（`orderStatusName` / `statusName` / …）依次尝试，取不到就显示「数据缺失」，不会编造。

### 6.4 返回值处理 `present`

技能要求「只用 `payOrderQrCodeUrl`，禁止展示 `payOrderUrl`」→ 交给模型前递归删掉 `payOrderUrl`。模型看不到，自然不会展示。

## 第 7 步：宿主适配说明 `src/cooker/luckin/host_adapter.md`

逐条声明技能里哪些规则在 COOKer 不适用、用什么替代：

| 技能原规则 | COOKer 中 |
|---|---|
| Token 读取优先级、询问是否保存到 `~/.my-coffee/`、让用户发 Token | 全部不适用：Token 由宿主配置文件管理，不向用户索要、复述、保存 |
| curl 兜底调用、ipinfo.io 按 IP 定位 | 没有命令行。问用户位置；用户只给地名时可用其大致经纬度（粗定位，不展示距离） |
| 确认门店和商品后「确认下单意图」一次 | 由系统确认卡完成这一次确认；不要在文字里再问「确认吗」 |
| 支付二维码按渠道能力展示 | 本界面支持 Markdown 图片：`![支付二维码](url)` + 链接 |
| 调用隐身 | 界面会显示工具调用摘要（系统行为），回答文字仍不提工具名 |

还有两条 COOKer 通用规则：【】只给菜谱名；不与其他品牌比较。

## 第 8 步：接线与前端

- `skills.py`：技能的工具与适配说明不再写死麦当劳，改为遍历 `all_connectors()`。新增服务时这里不用改。
- `verify.py`：「本轮调过外部服务就跳过无括号菜名扫描」改用 `connector_tool_names()`。
- 中断类型 `mcd_confirm` → `action_confirm`，并带上 `connector` 字段。CLI 的 `ask()` 同步改。
- 前端 `mcd-confirm.tsx` → `action-confirm.tsx`：按 `connector` 显示 🍟 / ☕，「应付」与「实付」一样标红。
- `lib/cooker.ts`：瑞幸 8 个工具的中文标签（写工具标「需确认」）。

## 第 9 步：测试 `tests/test_luckin.py`（10 个）

假服务按第 3 步实测的真实结构构造（门店、预览字段、元）。覆盖：

1. 加载 `my-coffee` 只绑定瑞幸 8 个工具，系统提示词里只有瑞幸正文
2. 快照里没有 `returnDirect`
3. 只读工具走完整 MCP 协议
4. 下单卡来自实时预览（应付 ¥16.00、减免 ¥4.00、自动使用 1 张券），且此时只调用了 `previewOrder`
5. 确认后：**模型没传的券码被透传、坐标被换成门店坐标**、结果里没有 `payOrderUrl`
6. 预览明细与下单参数不一致 → 拒绝，不弹卡
7. 门店打烊 → 卡片提示
8. 确认期间应付金额变化 → CHANGED，不下单
9. 取消：先查订单再出卡，确认后只执行一次
10. 瑞幸冻结不影响麦当劳

全量 92 个测试通过（已验证）。

## 局限与下一步

- 订单详情字段名、支付二维码 URL 的形态，要等一次真实下单才能核对。
- 位置靠用户描述 + 模型估计坐标。更准确的做法是前端经用户授权调用浏览器定位，把坐标随运行上下文传给后端（已记入 P5）。
- 技能描述里有「点单、下单、门店」这类泛词，和麦当劳请求可能混淆；本次两条真实用例路由正确，但还没有系统评测（已记入 P5）。
