# COOKer：Agent + RAG 简历与面试准备

整理日期：2026-10-27。依据当前工作区实现、已有评测报告与技术决策记录。本文是简历和面试材料，不表示新增了系统功能。

## 1. 简历正文

**COOKer｜具备长期记忆与约束执行能力的烹饪 Agent**

**技术栈：**Python、LangGraph、LangChain、Pydantic、FastMCP、NumPy、Next.js。

**项目简介：**基于 HowToCook 构建个人烹饪 Agent，围绕 372 道菜谱实现食材推荐、做法查询、人数换算及购物清单生成，结合混合检索、跨会话偏好记忆与人工确认，提供 Web、CLI 和 MCP 使用入口。

- **Agent 执行编排：**基于 LangGraph 构建 agent/tools/verify 状态图，接入 9 个工具，完成模型决策、工具执行与结果回灌；将用量换算、清单合并等确定性任务下沉至领域服务，通过纠错上限与图步数限制控制异常循环。
- **RAG 检索链路：**实现结构化预过滤、BM25/向量召回、RRF 融合、文档聚合与重排，按菜谱章节切块并保留命中证据；在 31 条自建检索样本中，25 条菜谱查询 Hit@1 从 BM25 的 0.68 提升至 1.00，并支持向量及重排故障降级。
- **记忆与约束执行：**使用 Checkpointer 管理会话状态、Store 保存跨会话偏好，动态注入档案并按约 12K token 预算裁剪历史；工具层自动合并过敏原与忌口条件，移除过敏原时通过 interrupt/resume 完成人工确认与恢复。
- **回答校验与行为评测：**通过确定性规则核对菜名存在性及其与工具结果的关联，失败时反馈重答，缺少查询依据时强制调用工具，最多纠错两次；构建 12 场景×3 次的行为评测，已有 Qwen、DeepSeek 报告均通过 36/36。
- **结构化入库与增量缓存：**采用规则解析与 LLM 语义抽取分工，通过 Pydantic 校验及归一化生成领域数据并保留原文；抽取缓存绑定内容哈希与 Prompt 版本，向量缓存按文本哈希及模型签名复用，配合受限并发减少重复 API 调用。

字数受限时，可删除最后一条，将“规则解析与 LLM 结构化抽取入库”合并进 RAG 条目。面试中优先展开 Agent 编排、RAG、记忆与人工确认、回答校验四条主线。

## 2. 约一分钟的项目介绍

我做的是一个基于 HowToCook 的个人烹饪 Agent。用户可以用自然语言完成选菜、查做法、换算人数和生成购物清单，它还会跨会话保存忌口、过敏原和常用人数。

我重点解决三个问题。第一是任务执行：用 LangGraph 显式组织模型和 9 个工具的调用循环，数值换算和清单合并由程序执行。第二是知识获取：规则和 LLM 配合结构化入库，检索时先按条件过滤，再做 BM25、向量召回、RRF 和重排。第三是可靠性：在工具层应用用户约束，对放宽过敏约束的操作要求人工确认，并用代码校验回答中的菜名是否有工具依据。

我用检索消融和重复场景评测验证效果。自建检索集有 31 条，其中 25 条菜谱查询的 Hit@1 从 BM25 的 0.68 提升到完整链路的 1.00；Agent 的 12 个场景各重复 3 次，保存的两个模型报告都是 36/36。这些数据只代表小样本下的检索和行为结果，目前还没有完整的回答忠实度评测。

## 3. 先记住完整调用链

### 在线 Agent

用户消息 → 按 thread_id 恢复状态 → 按 user_id 读取档案 → 构建系统提示词并裁剪模型输入 → 模型返回工具调用或回答。

工具调用 → ToolNode 执行 → ToolMessage 回写 → 再次调用模型。

最终回答 → verify 检查 → 通过则结束；不通过且未超过纠错上限，则删除回答、附反馈并重答；达到上限仍失败则追加未核对说明。

### 检索

工具读取档案并合并约束 → RecipeStore 筛选候选文档 → 在候选块上进行 BM25 和向量打分、各取 top-50 → RRF(k=60) 融合 → 按 doc_id 聚合，文档取最佳块分数并保留两个证据块 → 前 20 个文档参与重排 → 返回 top-k 摘要和片段。

代码当前顺序调用向量与 BM25；“双路召回”不等于已实现并发召回。做法详情由 get_recipe 返回原文结构，搜索工具主要用于发现候选与提供片段。

### 离线数据

Markdown → 规则解析 → 通过内容哈希与 Prompt 版本查抽取缓存 → 未命中时进行 LLM 结构化抽取、校验、重试与主备降级 → 保存菜谱与技巧数据 → 按章节切块 → 复用或生成 embedding → 写索引。

缓存复用意味着减少重算；当前流程仍会重写完整数据文件、重建索引产物，不是数据库级在线增量更新。

## 4. Agent 执行编排：基础到深入

### Q1：这为什么算 Agent？和普通 RAG 有什么区别？

模型会依据用户意图选择工具、生成参数，再根据工具结果决定继续调用还是作答。例如“做三个人的量并列清单”需要执行换算或清单工具；“记住我花生过敏”需要更新档案。RAG 是其中获取知识的一类工具能力，整个 Agent 还负责执行动作和维护状态。

不要声称实现了独立规划器或复杂任务分解器：当前是单 Agent 的工具调用循环。

### Q2：为什么不直接用框架的一行式 Agent？为什么不做多 Agent？

我复用了 LangGraph 的状态管理和 ToolNode，但显式定义 agent、tools、verify 三个节点，便于插入校验、指定重答路径以及观察状态变化。当前只有 9 个工具，单 Agent 足以完成路由；多 Agent 会增加模型调用、状态传递和错误来源，当前没有评测证据支持这项复杂度。

自主设计的是业务状态图与策略；底层图执行、持久化、工具调度由框架提供。

### Q3：工具什么时候并发？写档案和查菜能一起调用吗？

ToolNode 支持同轮多个工具调用的并行执行，适合互不依赖的查询。但当前没有实现按副作用分类的自定义调度器。如果同一轮同时更新档案和推荐，推荐可能读到旧偏好；两个档案更新也可能发生读改写覆盖。

改进方案是将写入与依赖写入结果的查询分阶段执行，对同一用户的档案更新做串行化或版本控制。必须把这些作为改进方向，不能说当前已经保证一致性。

### Q4：怎么防止无限循环和费用失控？

校验纠错每轮最多两次；CLI 和现有评测配置了 recursion_limit=30，图执行步数超限后中止。步数不等于模型调用次数，也不等于金额预算。当前没有完整的单任务费用预算、统一截止时间和调用配额，生产化时需要补齐。

### Q5：为什么换算不让模型做？

语言模型负责理解意图和调用工具，程序负责可复现的运算。用量区分 per_person、per_serving、fixed、to_taste，购物清单只合并归一化后同名同单位的食材，不擅自换算 g 与“个”。计算可测，但输入来自模型抽取，仍可能存在抽取误差。

## 5. RAG：重点准备的连续追问

### Q6：为什么要先做结构化抽取？

语义相似不能可靠表达“不含花生”“30 分钟内”和人数换算。标题、原文步骤等格式明确的字段用规则解析；用量语义、口味等字段由模型抽取，供过滤、计算和检索概览使用。原文同时保留，避免只有模型加工后的数据可查。

Pydantic 解决结构合法性、类型及部分归一化，不证明模型理解的事实正确。需要抽检和独立标注来进一步评估。

### Q7：切块为什么按章节？块越小不是越好吗？

菜谱有概览、用量、步骤分组和附加内容，优先按自然结构切块，再按条目或段落装箱，软上限约 700 字符。每块带菜名与章节前缀，让“加啤酒炖煮”这类步骤保留所属菜谱信息。小块便于匹配局部细节，但会损失上下文，因此检索后按文档聚合并保留证据块。

这个上限是工程选择，没有切块粒度的独立消融，不能说它已被证明最优；单条很长的步骤也可能超过软上限。

### Q8：为什么先过滤再检索？

先确定符合约束的菜谱 ID，再在对应块上排序，避免全库 top-k 之后才过滤导致结果不足。这里是“候选资格先过滤”，当前 NumPy 向量计算仍对全矩阵做点积，再用 mask 排除候选外结果；因此不能宣称预过滤已减少向量计算量。

过滤可能受抽取误差和标签漏标影响。候选为空时应解释约束、必要时请求用户调整；过敏等约束不能为了凑结果自动放宽。

### Q9：为什么用 RRF，不直接把分数加起来？

BM25 与余弦相似度量纲和分布不同，直接相加需要归一化和权重标定。RRF 只使用名次，公式是 score(d)=Σ 1/(60+rank_i(d))，实现简单，适合没有足够训练数据的小项目。代价是丢掉分数差距，某一路高度自信的第一名与勉强排第一的结果无法区分。

### Q10：你说混合有效，为什么结果反而不如纯向量？

现有报告中纯向量菜谱 Hit@1 是 0.88，RRF 混合是 0.76。部分同义词查询的 BM25 排名错误，RRF 只看名次，使融合排序受到影响；二者整体 Hit@5 都是 0.96。加入重排后该小样本的 Hit@1 到 1.00。

保留 BM25 是因为精确词匹配和无网络降级仍有价值。这个结果说明需要分别检查召回与排序，不能把“混合一定更好”当作前提。

### Q11：重排能补回没召回的答案吗？具体给它什么？

重排只对候选重新排序，不能补回未进入候选的文档。当前按文档取最佳融合块分数，前 20 篇进入重排；每篇用概览加命中证据组装，最多 1500 字符。保留两个证据块有利于控制成本，但也可能截掉关键信息，这些参数还没有系统调优。

### Q12：为什么不用 Milvus 或 HNSW？十万块后还能跑吗？

当前索引元数据是 1761 块、1024 维，float32 原始向量约 7.2MB，适合 NumPy 精确检索。复杂度包含 O(Nd) 点积和当前 O(N log N) 全排序，在线耗时还包括 embedding、重排与模型生成。

规模扩大后应测吞吐、P95/P99、内存和数据更新需求，再考虑向量数据库与 ANN。十万块只是重新评估的量级参考，不能当作固定迁移阈值。迁移还需要验证过滤与 ANN 的召回率。

### Q13：embedding 或重排服务挂了，具体发生什么？

在线向量调用失败时返回空向量排名，由 BM25 继续；重排失败时保留融合顺序。两个依赖分别计数，连续两次失败后冷却 60 秒，到期允许再次请求。评测发现降级统计不为空就将该轮检索结果作废，避免把降级链路当成完整链路对比。

当前是轻量单进程实现，没有锁和半开请求配额；并发到期时可能多请求同时探测，不能称为严格的单探针熔断器。启动时的无效模型配置、索引签名不匹配等错误，也不属于这条在线降级路径。

### Q14：31 条评测是不是太少？1.00 有什么意义？

是小样本：25 条菜谱、6 条技巧，来自开发者自建问题。每条有可接受文档 ID 集合，检查第一个正确答案的名次，报告 Hit@1、Hit@5、MRR@5 和平均耗时。1.00 只表示这份样本上有效，不能证明泛化，更不能代表最终答案准确率。

下一步需要冻结独立测试集，补真实用户问题、长尾同义词、约束组合与无答案问题；按类别报告结果，并测分位延迟。报告里的约 493ms 是菜谱检索均值，约 598.6ms 是技巧检索均值，都不是整轮对话延迟。

## 6. 记忆、约束与人工确认

### Q15：长期记忆为什么不用向量库？

需要记住的是过敏原、忌口、人数等少量明确字段，键值读取比语义召回更确定，也更容易修改和过滤。短期状态按 thread_id 保存，档案用 namespace=("users", user_id) 存储，每次模型调用前读取。

同一运行环境内可以跨会话共享档案；CLI SQLite 与本地 LangGraph Server 状态不自动同步。Web 默认共用 local 档案，目前没有完整多用户身份与权限隔离。

### Q16：12K 裁剪等于无限上下文吗？怎么保护工具消息？

这是对模型输入历史的预算裁剪，丢弃较早轮次，不是语义压缩或无限上下文。状态中的旧消息仍可保留，但没有全部发送给模型。使用 trim_messages 从用户消息开始裁剪，降低出现无对应 tool_call 的 ToolMessage 的风险。

12K 是近似历史预算，未包含另行添加的系统提示和工具 schema，不能当作整个请求的精确 token 上限。未来可增加摘要或按需历史检索，并对复杂消息序列做边界测试。

### Q17：模型不传过敏参数怎么办？是否所有工具都强制过滤？

search_recipes、browse_recipes 和 recommend_by_ingredients 的工具层读取档案并合并排除条件，模型漏传也会执行。get_recipe 是点名详情查询，不拦截，而是返回 profile_warning。scale_recipe 与 make_shopping_list 主要负责计算，当前没有统一的过敏冲突检查。

过滤基于已有标签，标签由关键词推导，可能漏标。准确表述是“已记录约束在相关工具中自动应用”，不是保证食品过敏安全。

### Q18：为什么添加不用确认，删除要确认？

添加过敏原会收紧后续推荐条件，移除则会放宽，所以后者引入人工确认。interrupt 暂停图并依赖 checkpointer 保存状态，CLI 或 Web 收到确认问题，再用同一线程的 Command(resume=答案) 恢复。

恢复时中断所在节点或工具从头重新执行，interrupt 前只读取、不写入。这个设计规避当前流程的提前写入，并不自动获得所有外部动作的 exactly-once 语义。

### Q19：确认期间用户档案又改了，怎么保证确认的是同一件事？

当前没有档案版本和确认对象版本的校验。若并发修改，需要确认内容绑定版本号，恢复后重新检查；冲突时重新确认。对有外部副作用的动作还应增加操作 ID、幂等记录和事务设计。这属于生产化改进，不能说当前已完成。

## 7. 回答校验与评测

### Q20：verify 到底验证什么？为什么不再调一个模型判断？

它验证【菜名】是否在库中、对应名称是否出现在历史 ToolMessage 文本里，并扫描部分未加括号的库内菜名。存在性检查可由程序确定，无需增加模型裁判的调用和不确定性。

它没有证明步骤、原料、推荐理由和数字正确；历史任意工具文本中出现过名称也不等于取回了完整做法。当前基于文本匹配，若要增强应将工具结果转换成结构化 evidence ledger，记录文档 ID、工具、字段和时间，再校验回答中的具体事实。

### Q21：为什么失败后要强制调用工具？模型不是会自己改吗？

对“库内菜没有查询依据”这类问题，单纯要求重写可能再次无依据作答，所以用 tool_choice=required 保证本次至少产生工具调用；只有库外名称问题时允许直接改写。required 不能保证选对工具、参数正确或结果充分。

Qwen 适配器曾将 required 改为 auto，代码在绑定工具后显式覆盖请求参数，并有回归测试。面试可以展示这个兼容性处理，但不要扩大成自研多协议模型网关。

### Q22：失败回答已经流出去了，删除还有什么用？

删除图状态中的回答可以避免它留在后续上下文和最终状态里，但无法撤回用户已经看到的流式文本。当前仍可能短暂显示未通过校验的草稿。更严格的交付可以先缓冲最终正文、通过校验再展示，或清晰标记草稿；需要权衡首字延迟。

### Q23：36/36 到底测了什么？是不是全正确？

12 个场景各重复三次，主要检查工具选择、部分关键参数、档案实际写入、过敏冲突提示，以及括号菜名与工具结果的关联。不是完整回答质量评测。已有报告没有覆盖所有 HITL、长历史、故障组合和描述忠实度；HITL 等行为另有离线测试覆盖。

旧模型逐步加入 verify 与强制工具后的 26/36→30/36→34/36 是技术决策文档记录的历史实验，并非本次重新运行；最终两模型 36/36 来自已保存报告。一次多轮场景判定修订已在脚本和文档注明，因此不能说整个迭代过程是严格盲测。

## 8. 入库与缓存

### Q24：怎么降低更新成本？改模型后缓存会不会错？

抽取缓存键使用 Prompt 版本和原文哈希，命中时不再调用模型；embedding 缓存按模型名和维度分文件，再按块文本哈希查向量，构建时分段保存。现有入库报告记录 372 条抽取均命中。

抽取缓存键没有自动包含模型 ID 和完整 Schema 哈希，切换模型想重抽取时需要手动更新版本或清理缓存。embedding 签名是模型名加维度，不包含接入端点或厂商背后静默更新的权重版本，也有失效边界。

### Q25：中途失败和发布新索引怎么处理？

抽取用 Semaphore(8) 限制在途调用，单条失败会被记录而不取消整批；格式错误先在单厂商内重试，总尝试上限两次，再进入主备降级。抽取缓存使用临时文件替换，embedding 缓存按批保存，便于重跑复用。

当前最终索引的 chunks、vectors、meta 并非作为一个原子版本一起发布，更新时要求停服务、重建、重启。在线化应使用新版本目录构建并验证、原子切换版本入口，失败时保留旧版本。

## 9. 模拟“压测式追问”

## 10. 三个可讲的真实设计故事

### 故事一：混合检索没有自动变好

现象：纯向量 Hit@1 0.88，混合反而 0.76。

定位：分类查看同义词等查询，BM25 错误靠前结果影响 RRF；融合不用原始分数，无法辨别一路排名置信度。

处理：保留混合召回与 BM25 降级能力，用重排改善候选顺序；在现有小样本中达到 1.00。

反思：补独立测试集、Recall 与排序分层指标、重排延迟与成本消融，避免只凭最终 1.00 下结论。

### 故事二：Prompt 要求查工具，模型仍然没查就答

现象：技术决策记录中旧模型仅靠 Prompt 为 26/36。

处理：加入确定性 verify，再针对缺查询依据的反馈强制工具调用，历史记录逐步达到 30/36、34/36；后续模型对照也显示模型本身的影响。

反思：代码约束只覆盖可确定判断的部分，不能把菜名有依据等同于所有描述忠实，也需要处理流式草稿暴露。

### 故事三：持久化不能只用内存测试

现象：SQLite 持久化中出现事务模式冲突。

处理：根据 Saver 与 Store 的事务管理方式使用独立连接，Store 连接启用 autocommit，并增加真实 SQLite 的中断、恢复、重开连接后读取的端到端测试。

反思：内存实现能验证状态逻辑，但无法替代实际存储层的一致性与恢复测试。这个修复不表示已验证高并发写入能力。
