# 面试知识点（按阶段积累，只记录已实现的内容）

## P0 数据层与模型接入

**Q：为什么不直接把菜谱全文丢给向量库，而要做结构化抽取？**
向量检索擅长「语义相似」，不擅长精确约束：「30 分钟内」「不含花生」「我有土豆和鸡蛋」需要结构化字段做过滤和计算；「做 5 人份」需要每份用量。所以规则解析确定性字段，LLM 抽取语义字段，原文保留用于检索与引用。

**Q：LLM 抽取的结果如何保证质量？**
① Pydantic Schema + function calling 约束结构；② 枚举词表 + 校验器归一化；③ 格式错误同厂商重试、再降级；④ 全量后做分布统计和抽检（发现过敏原误标，改为规则推导）；⑤ 回归测试。局限：用量换算仍可能有误差，没有人工标注的评测集——P4 补充。

**Q：增量更新怎么做？**
缓存键 = Prompt 版本 + 原文哈希。上游更新只重算改动的菜；改 Prompt 递增版本号使缓存整体失效。实测二次运行 372 条全部命中、0 token。

**Q：fallback 为什么要在 with_structured_output 之后？**
`with_fallbacks` 返回的 `RunnableWithFallbacks` 不是 ChatModel，没有 `bind_tools`/`with_structured_output`；且主备模型都必须输出同一结构。所以先对每个模型做 transform 再组合。

**Q：并发调用怎么控制？**
`asyncio.gather` 并发 + `asyncio.Semaphore(8)` 限制在途请求数（类比 Java `Semaphore`），防止触发厂商限流；单条失败捕获记录，不影响整体。372 条约 220 秒。

**容易被追问暴露的点**
- 过敏原是关键词规则，会漏标——不能说「保证安全」。
- `total_time_minutes` 是模型预估，不是原文事实。


## P1 检索层与 MCP 工具

**Q：为什么不用向量数据库？**
数据量 1731 块、7MB，暴力余弦是精确 top-k 且毫秒级；ANN 是拿精度换速度，小数据没必要。说清楚迁移阈值（十万级块 / 多进程共享 / 在线增删），以及 `_vector_rank` 是唯一替换点。

**Q：混合检索为什么用 RRF？**
BM25 分数无上界、余弦在 -1~1，直接加权要先归一化，而分数分布还随查询变化。RRF 只看名次，`1/(k+rank)`，k=60 让多路都排前面的文档胜出，又不让某一路的第一名独占。

**Q：父子检索解决什么问题？**
大块召回不准（一道菜混了原料、步骤、附加说明），小块又缺上下文。小块召回 + 菜名前缀 + 按菜聚合，返回整道菜和命中片段。

**Q：外部模型服务挂了会怎样？**
向量失败退回 BM25，重排失败保留 RRF 顺序；熔断器连续失败 2 次断开 60 秒，之后半开试探。项目里真实发生过（embedding 403 / rerank 欠费），这正是加熔断的原因。

**Q：为什么换算和推荐不让 LLM 做？**
确定性问题用代码：可复现、可单测。LLM 负责理解意图、选工具、组织回答。推荐里的多样性重排是 MMR 思想：兼顾单项相关性和结果集的整体覆盖。

**Q：MCP 是什么？工具怎么设计？**
Model Context Protocol：把工具、资源以标准协议暴露给任意 LLM 客户端（类比「AI 的 USB 接口」）。工具描述会直接发给模型，决定它何时调用哪个工具，所以要写清用途和区别（如 search_recipes 与 recommend_by_ingredients）；错误转成可读的 ToolError，模型才能自我修正；返回值精简，节省上下文。

**如实说明的局限**
- 有消融评测（BM25 / 向量 / 混合 / 混合+重排，TD-14），但只有 31 条自写样本；引用数据时要同时说明样本规模。
- 发现过「混合不如纯向量」的反直觉结果，能解释原因（RRF 只看名次）以及为什么仍保留 BM25——这是很好的面试素材。
- 评测集只有 31 条、由开发者自己编写，存在偏差。
- 同义词表手工维护，覆盖有限。

## P2 LangGraph Agent

**Q：讲一下你的 Agent 执行循环。**
StateGraph 三个节点：agent（模型决定调工具还是作答）→ tools（ToolNode 并行执行，结果作为 ToolMessage 回写）→ 回到 agent；
不再调工具时进入 verify，代码检查回答引用的菜是否有工具依据，不通过就删掉回答、附上具体问题让模型重答，最多 2 次。
防死循环：verify 重答上限 + recursion_limit=30。

**Q：怎么防止模型幻觉？**
三层：① Prompt 约束「先查再答」；② 【菜名】引用约定 + 确定性校验；③ 校验失败后用 `tool_choice=required` 强制调工具重答。
用评测量化每一层：qwen-plus 只靠 Prompt 26/36 → 加 verify 30/36 → 加强制调工具 34/36。
诚实补充：verify 只查菜名存在性，不查描述正确性，仍出现过「这道菜能用上土豆」这类错误。

**Q：Prompt 和代码约束怎么分工？**
能用代码判断的就不交给模型：过敏原过滤、用量计算、菜名存在性。Prompt 负责模型擅长的部分：理解意图、选工具、组织语言。
过敏属于安全问题，即使模型忘了传参数，`_filter()` 也会强制排除。

**Q：长期记忆怎么实现？**
LangGraph Store，namespace = ("users", user_id)，存结构化档案；每轮读取写进系统提示词。
短期记忆是 checkpointer 按 thread_id 存消息，发给模型前 trim_messages 裁剪，start_on="human" 保证 tool_call 与结果成对。

**Q：人在回路怎么做？要注意什么？**
`interrupt()` 暂停图并把状态写进 checkpointer，前端拿到问题，用 `Command(resume=答案)` 恢复。
坑：恢复时节点（这里是工具）**从头重新执行**，interrupt 之前不能有副作用，否则会执行两次。

**Q：评测怎么做的？**
12 个场景、每个跑 3 次（模型输出有随机性，单次结果不可信），只判可客观验证的行为：调了哪个工具、参数、档案是否写入、引用是否有依据。
发现过「检查规则太宽松导致 12/12 但实际有幻觉」——之后才加入引用校验。Qwen 与 DeepSeek 对比：DeepSeek 36/36、verify 0 次介入、速度快一倍。

**排查故事（可讲）**
- SQLite 事务冲突：内存版测试没覆盖，第一次修复判断错误，读源码找到 isolation_level 差异。
- langchain-qwq 把 required 静默改成 auto：通过打印最终请求参数发现，直连 API 验证后绕过并加回归测试。

**如实说明的局限**
- 评测 12 个场景是自己写的，规模小；没有回答忠实度（描述正确性）的自动评测。
- 流式输出时被驳回的草稿可能先显示给用户。

## P4 技能按需加载与麦当劳接入

**Q：Agent 要接一个新领域（麦当劳），为什么不直接把规则写进系统提示词，或加一个路由模型？**
规则全写进去会稀释原有提示词，而且每轮都付 token。我用渐进式披露：系统提示词只有技能的一行描述，模型判断命中后调 `load_skill`，
之后才注入技能正文、绑定 36 个工具。路由由同一个 ReAct 循环里的模型完成，不需要额外 LLM 调用，也不需要正则判断意图。

**Q：工具是怎么来的？36 个都手写吗？**
不手写。脚本调 MCP 的 `list_tools` 拿官方入参结构存成快照，`StructuredTool` 直接用 JSON Schema 作为 args_schema。
快照让绑定离线可测；每次真实调用前再用线上结构做 jsonschema 校验，服务端改了契约就明确报错，而不是猜参数。
第一次同步就发现文档里的工具名有 4 处已过时，硬编码会直接失败。

**Q：怎么保证「花钱 / 扣积分」的操作不被误执行、不被重复执行？**
三道关：① 确认卡由代码用实时查询生成（下单前重新算价、抽奖前重读资格），不让模型写金额；② interrupt 暂停图，恢复时工具会从头重跑，
所以把卡片指纹发给前端、确认时带回，重跑后指纹不一致就不执行；③ SQLite 台账以 tool_call_id 为幂等键，`BEGIN IMMEDIATE` 原子认领，
请求发出后超时记为 UNKNOWN 并冻结账户所有写操作，只能人工核实后用命令解冻（不做成工具，模型无法自行解冻）。

**Q：为什么超时不能重试？**
写请求可能已到达服务端，抽奖接口没有幂等键，重试等于可能重复扣分。「不知道」必须作为一个独立状态，而不是当作失败。

**Q：怎么测试会花钱的功能？**
用 FastMCP 在内存里起一个假的麦当劳服务，走真实 MCP 协议，数据取自真实返回结构样例。测试覆盖：确认后只执行一次、取消不执行、
确认期间消耗变化不执行、资格不足不弹卡、超时冻结与解冻、崩溃重放不重发、同步和异步两条执行路径。真实账户上只做只读查询与「弹卡后取消」。

## 聊天中的菜品图片

**Q：回答里要配图，为什么不让模型直接输出图片 Markdown？**
图片地址是确定性数据，交给模型抄写就有出错和编造的可能，还多花 token。我让模型只按约定写【菜名】，前端在回答结束后按菜名批量向菜谱库取封面——和菜谱抽屉不经过 LLM 是同一个原则：确定性的数据由代码取，模型只负责表达。

**Q：前端怎么避免重复请求？**
三层：流式输出期间不请求（菜名逐字增长会反复触发）；页面级缓存，连「这道菜没有图」也缓存；请求中去重——同一个菜名已在请求中，后来者等同一个 Promise（single-flight）。最后一层是实测发现的：React 严格模式让 effect 执行两遍，缓存还没写入，同一批菜名发了两次请求。

## 接入第二个外部服务（瑞幸）

**Q：接第二个服务时你怎么组织代码？**
先比较两者差异：调用、结构校验、确认卡流程、台账完全相同，不同的只有地址、凭据、读写白名单、确认卡内容。于是把麦当劳的实现提成通用层 `connectors/`，
每个服务只写一个 `Connector` 描述（瑞幸 115 行）。重构有原来 17 个测试兜底，断言一个没改就全部通过，才说明行为没变。

**Q：技能文档里的规则，怎么判断哪些交给提示词、哪些写成代码？**
能被代码机械检查的都写成代码：瑞幸要求「预览返回的券码必须原样透传」「下单用门店坐标」「不展示 payOrderUrl」——这些在确认卡生成时由代码改写参数和结果，
模型漏传也不会出错；需要理解语境的（追问位置、外送意图要拒绝、规格识别）留给提示词。

**Q：第三方技能和你的运行环境冲突怎么办？**
瑞幸技能假设宿主能执行 curl、按 IP 定位、把 Token 写到用户目录；我的 Agent 没有 shell，Token 由宿主配置文件管理。
技能许可证禁止改动，所以正文原样保留，在宿主适配说明里逐条声明哪些规则不适用、用什么替代，并让适配说明优先级高于正文。

## 工具结果里的图片：content 与 artifact

**Q：工具返回里有图片，你怎么展示？为什么不让模型输出 Markdown 图片？**
LangChain 工具可以返回 `(content, artifact)`：content 发给模型，artifact 只存进 ToolMessage 给界面用。我把图片提取进 artifact，
并从 content 删掉图片地址——模型不需要它们，删掉后麦当劳菜单的模型输入少了约 34%，也杜绝了模型抄错或编造图片地址。
界面只显示回答里提到的商品，避免把搜索到的全部商品都贴出来。

**Q：显示外部返回里的图片有什么安全问题？**
浏览器加载图片就会向那个地址发请求，外部返回里若混入任意 URL 就能做追踪。所以只放行 https 且属于官方图床的域名，
域名判断要写成「等于或以 `.域名` 结尾」，防止 `xxx.com.evil.example` 这种后缀伪装；前端再加 `referrerPolicy="no-referrer"`。

**排查故事（可讲）**：真实测试偶发不出图。没有靠重跑了事，而是推理出 verify 重答时插入的隐藏用户消息截断了「一轮」的边界，
构造预置会话确定复现，并用「只回退一行」的干净对照证明修复有效。

## 图片就地展示；从官方文档补连接器

**Q：图片怎么和对应的文字放在一起，又不让模型输出图片地址？**
在 react-markdown 的 rehype 阶段（HTML 语法树）写插件：按【菜名】链接和商品名找到它所在的列表项 / 单元格 / 段落，插入 `<img>`。
模型只需要像平时一样写名称；位置由代码按语法树确定。还要处理「列表项里第一个名称没图、第二个有图」的情况，否则图片会被误认为属于第一个。

**Q：MCP SDK 把 HTTP 401 吞成了笼统错误，怎么给用户明确提示？**
传输层允许注入 httpx 客户端工厂，我挂了响应钩子记录状态码，失败时据此提示「Token 过期」或「被限流」。但写请求已经发出时一律按「结果未知」处理，错误码不能证明没执行。

**排查故事（可讲）**：加钩子后离线测试全过，真实调用却全部失败——fastmcp 调用工厂时多传了一个参数，签名不兼容。教训是假服务测不到和真实库的接缝，改接缝必须真实跑一次，并把真实调用方式写成测试。

**Q：后端 ID 返回给前端要注意什么？**
JS 数字只能精确到 2^53，瑞幸 19 位订单号解析后会被改写。优先用接口给的字符串 ID（`orderIdStr`），自己的接口也应把大整数序列化成字符串。
